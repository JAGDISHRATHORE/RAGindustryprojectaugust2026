# ADR 0002: Structure-aware chunking and checklist decomposition

Status: accepted

## Context

Fixed-size chunking (for example 512 tokens with overlap) cuts legal text in
the middle of enumerations. Art. 14(4) has five lettered points; a chunk
boundary between (d) and (e) loses the stop requirement. Policies have the
same issue at a smaller scale.

Obligations are also too coarse to judge directly. Art. 10(2) contains eight
separate requirements (points a to h). "Is Art. 10(2) met?" invites a vague
answer.

## Decision

* **Regulation:** one chunk per numbered paragraph. The parser looks for the
  next expected paragraph number after a sentence end, which avoids false
  splits on references like "Article 72." (`ingestion/regulation.py`, tested
  against the paragraph counts of Articles 9 to 15).
* **Company documents:** one chunk per `##` section, with the heading kept in
  the chunk text. Long sections are split on paragraph breaks only. Chunk ids
  are stable (`<doc_id>#s<section>`), so citations survive re-indexing.
* **Obligations:** every assessed paragraph is broken into atomic checklist
  items in `data/obligations/ai_act_high_risk.yaml`. The legal text itself is
  attached at load time from the regulation file, so the catalog cannot drift
  from the law.

## Consequences

* "Partial" verdicts name the missing item (for example `stop`), which is what
  makes the report actionable.
* Each checklist item doubles as a search query (query decomposition), which
  improves recall for multi-part obligations.
* Writing the checklist is expert work. That is intended: it is the part of a
  consultant's method that should be reviewed and reused, not regenerated by a
  model on every run.

## Alternatives considered

* **Semantic chunking by embedding similarity.** It adds cost and makes chunk
  boundaries unstable between runs, which breaks citations.
* **LLM-generated checklists.** Useful to draft a catalog for a new
  regulation. Generating them at run time would make verdicts non-reproducible.
